# 数据流水线

```
fetch → parse → validate → index → (qc)
  │        │        │         │
  │        │        │         └─ 索引 + FTS5，供检索
  │        │        └─ 写入前强制过 JSON Schema
  │        └─ PDF → 结构化 JSON
  └─ 官方公开源下载（仅落 data/raw/，绝不入库）
```

每一步都可单独重跑，产物可删可重建。

---

## 1. fetch — 抓取

```bash
elk fetch --only reading
```

只抓**官方免费公开的样题**（ielts.org 等由出题方自己发布、供考生练习的材料）。

### 踩过的坑（写死在代码注释里）

1. **Cloudflare 拦截的解法是降级 HTTP/1.1。** 改 UA / 加 Referer 全部无效，
   只有 `curl --http1.1` 有用。根因是对方对 HTTP/2 指纹做 bot 判定。
2. **下载必须做魔数校验**（PDF 检查 `%PDF-`）。否则会把 challenge HTML
   存成 `.pdf`，后续解析全线失败且极难定位。
3. **官方 URL 命名不统一**：阅读是 `general-reading`，写作却是 `general-training`。
   别顺手"统一"它们。
4. **官方 slug 有拼写错误**：`identifying-information-true-FLASE-not-given`
   （不是 false）。照抄官方拼写，改了就 404。

## 2. parse — 解析

两个解析器，覆盖两类版面：

| 解析器 | 输入 | 说明 |
|---|---|---|
| `parse_reading_access.py` | 无障碍大字版三件套 | text / question / answer 分离，解析成本最低 |
| `parse_reading_taskbank.py` | 分题型 task bank（学术 + 培训类） | 每题型一个独立 section |

### 踩过的坑（注释里记了 12 个，这里列最有代表性的）

1. **题组标题有三种形式**：`QUESTIONS 1 – 6` / `QUESTIONS 19 and 20` / `QUESTION 40`。
   只支持范围式会漏掉 15 题。
2. **填空题的编号嵌在句子中间**（`find 23        equally valuable`），
   后跟 ≥2 空格。只处理行首式编号会丢掉整组题。
3. **先压缩空白再找多空格 = 永远找不到**。必须在保留原始空白的文本上定位，
   再压缩生成 stem。
4. **补救逻辑的时序**：填空编号要在"判断有没有题目"**之前**补，
   否则题组已因 questions 为空被丢弃了。
5. **段落切分**：用"行长 >60 字符且以句号结尾"去切，753 词只切出 1 段
   （大字排版每行仅 20–40 字符）。实测**单空行 = 段落边界**。
6. **section 名的空格数不一致**（`Summary Completion: productive` 有单双空格变体），
   必须先归一化空白再比较。
7. **答案行有两种写法**：`33 transmitted`（无点）与 `1. experience`（带点）。
   只认前者会让三个 section 全部解析失败。

## 3. validate — 校验

```bash
elk validate "data/structured/reading/**/*.json" --schema reading-test
```

写入前**必须**过 schema。这是数据层唯一的强约束，没有例外。

### schema 的几处设计

- **`word_count` 下限是 150 不是 1500。** 最初按"合成母本池"的口径设了 1500，
  结果官方真题（753–905 词）全部被判非法。这个字段的语义后来明确了：
  官方完整真题 700–950 词，task bank 节选 250–900 词。
- **`not_official` 是 `const: true` 的合规硬约束。** 即使素材来自官方，
  我们的**解析产物**也不是官方发布物，必须标注。
- **`paragraphs` 是 `{label, text}` 对象数组**，不是字符串数组——
  Matching Headings 依赖段落标签 A/B/C。
- **可选字段不允许显式 `null`**，空值应整个不输出。

## 4. index — 索引

```bash
elk index
```

产出 `data/index.jsonl`（每约 87 token）+ SQLite FTS5 表。

索引**不含正文**。它的作用是让你先用 87 token 定位到题，再按需读单篇（6k token）。

## 5. qc — 质量关卡

0.1 只落地了一关：`extract_evidence`。

### evidence 算法式定位

零成本（不需要 LLM）：词袋 + IDF 加权 + 相邻句窗口。

**关键设计：必含词硬约束。**

第一版只看"与查询最相似的句子"，覆盖率 87.4% 看着挺好，
但自动抽检发现——39 道填空题里证据句**真含答案的只有 65%**。

加上"候选句必须包含答案词"的硬约束后，准确率到 **97%**（38/39）。

**教训：覆盖率必须配准确性抽检，否则是自欺。**

另一点：硬约束命中的候选，不再用 `min_score` 过滤。
因为 query 里混了 stem 的十几个词，答案只占 1–2 个，
加权重叠率会被稀释到阈值以下，导致明明能定位却返回空。

## 审计工具

`src/elk/eval/` 下有一组数据质量审计脚本，判据分三类：

| 判据 | 抓什么 |
|---|---|
| 分布形态 | 满分占比（应 <1%）、半档占比（应 30–50%）、相邻档是否断裂 |
| 维度独立性 | 维度间相关性、取值完全相同比例、差值正负对称性 |
| 配对性 | 输入与标签是否真的对应（概念词命中率） |

**这三类必须都查。** 只查相关性会漏——相关性低只能说明两个维度不耦合，
不代表它们各自是好的。chillies 的 `r(TR,CC)=0.489` 看着健康，
但 TR 单独有 15% 是满分。

最致命的往往是**交叉证据**：`TR=9.0 的样本里 overall=6.0 有 171 篇`——
满分维度配 6 分总分，在一篇作文里不可能。
